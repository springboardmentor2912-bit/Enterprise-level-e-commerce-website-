SHOPSTACK Executive Summary & Table of Contents
SECTION 01

1. Executive Summary & Problem Formulation

Contemporary digital commerce demands high-performance, resilient multi-sided marketplace platforms capable of handling heterogeneous vendor catalogs, complex inventory allocations across distributed physical warehouses, dynamic multi-tier discount pricing, and fraud-resistant, cryptographically verified checkout payments. ShopStack is an enterprise-grade full-stack solution engineered to solve these architectural challenges with zero tolerance for race conditions or phantom stock deductions.

Market Challenges Addressed

  • Inventory Race Conditions: Eliminating overselling through atomic, idempotent payment verification stock deduction workflows.
  • Vendor Multi-Tenancy: Strict role-based isolation guaranteeing merchant catalog privacy and independent commission management.
  • Logistics Bottlenecks: Full multi-warehouse regional hub routing, pick/pack/ship tracking, and inbound quality control (QC).

Key Value Propositions

  • Secure Payment Integrity: Full integration with Razorpay SDK utilizing HMAC-SHA256 signature verification.
  • Unified Marketplace Checkout: Single multi-item transaction decomposing seamlessly into separate vendor orders.
  • Enterprise Auditability: Real-time financial ledgers, commission settlements, and comprehensive movement logs.

SHOPSTACK Authentication, Authorization & Security Architecture
SECTION 03

1. Stateless JWT Authentication Lifecycle

ShopStack implements a stateless JSON Web Token (JWT) architecture. Client requests submit credentials via /api/auth/login; upon verification against BCrypt hashed credentials in PostgreSQL, the backend issues an HMAC-SHA256 signed JWT containing the user ID, email, and designated security authority.

JWT Token Generation & Verification

public String generateToken(Authentication auth) {
  UserPrincipal user = (UserPrincipal) auth.getPrincipal();
  Date now = new Date();
  Date expiryDate = new Date(now.getTime() + jwtExpirationMs);

  return Jwts.builder()
      .setSubject(Long.toString(user.getId()))
      .claim("role", user.getAuthorities())
      .setIssuedAt(now)
      .setExpiration(expiryDate)
      .signWith(getSigningKey(), SignatureAlgorithm.HS256)
      .compact();
}

Security Filter Chain Execution

  • Extract Header: Authorization: Bearer <token> is intercepted per incoming HTTP call.
  • Cryptographic Validation: Secret signature and token expiration timestamps validated.
  • Context Hydration: SecurityContextHolder populated with UsernamePasswordAuthenticationToken.
  • Pre-Authorize Guard: Method-level constraints verify role permissions before controller dispatch.

1. Multi-Tenant Vendor Store Architecture

ShopStack accommodates independent vendor storefronts within a single marketplace domain. Each vendor is encapsulated by a VendorProfile entity, linking store branding, custom commission rates, approval statuses, and store-specific performance ratings.

1. Onboarding & Approval

Vendors register with credentials and submit store details. Accounts remain in PENDING status until verified by System Administrators, preventing unauthorized listings.

2. Strict Catalog Isolation

Backend Spring Data queries strictly filter modifications by the authenticated vendor's ID. Vendors cannot alter, view, or manipulate products belonging to rival merchants.

3. Performance Ratings

Aggregate store ratings are recalculated upon customer review submissions, dynamically displaying merchant trust badges across public product listings.

2. Product Catalog Taxonomy & SKU Lifecycle

Products are organized under standardized categories with dynamic slug routing and vector icons. Each item maintains operational attributes including stock levels, SKU codes, discount prices, and operational statuses.

Product Entity Lifecycle States

  • ACTIVE: Visible in catalog, available for cart addition and instant checkout.
  • OUT_OF_STOCK: Automatically triggered when stockQuantity == 0; cart actions blocked.
  • INACTIVE: Soft-disabled by the vendor for seasonal updates or pricing review.
  • DISCONTINUED: Archived permanently; historical orders preserved with immutable price snapshots.

Stock Adjustment Audit Trigger

public Product updateProductStock(Long id, int newQty) {
  Product p = productRepository.findById(id).orElseThrow();
  p.setStockQuantity(newQty);
  if (newQty == 0) {
    p.setStatus(ProductStatus.OUT_OF_STOCK);
    notificationService.sendStockAlert(p);
  } else if (p.getStatus() == ProductStatus.OUT_OF_STOCK) {
    p.setStatus(ProductStatus.ACTIVE);
  }
  return productRepository.save(p);
}

SHOPSTACK Pricing Engine, Cart & Promotional Coupon System

1. Shopping Cart & Dynamic Pricing Engine

The client maintains shopping cart state using persistent LocalStorage synchronized with backend live inventory validation. The pricing engine computes item subtotals, vendor taxes, promotional discounts, and shipping surcharges.

Mathematical Price Computation

ItemSubtotal = ∑ (EffectivePrice_i × Quantity_i)
OrderDiscount = min(DiscountValue, MaxDiscountCap)
NetPayableAmount = max(0, ItemSubtotal - OrderDiscount)

Where EffectivePrice uses discountPrice if present and strictly lower than regular price.

Cart Validation Constraints

  • Quantity Bound: Cannot exceed currently available stockQuantity.
  • Multi-Vendor Batching: A single customer checkout seamlessly decomposes into distinct vendor orders.
  • Stale Price Protection: Cart recalculates live backend prices before issuing payment tokens.

3. Automated Commission Calculation System

Upon successful order settlement, CommissionService automatically computes the platform revenue split. For an order amount $A$ and vendor commission rate $r\%$, the platform retains $C = A \times (r / 100)$, while the vendor payable balance is credited with $V = A - C$. Records transition from PENDING to SETTLED following delivery.

SHOPSTACK Order Processing, Idempotent Checkout & Razorpay Integration
SECTION 06

1. End-to-End Razorpay Payment Pipeline

ShopStack implements a high-security payment flow integrated with the official Razorpay Java SDK. All transactions are cryptographically signed and verified on the server side before confirming order states or altering inventory.

1️⃣ Step 1: Initialize Order
Client calls /api/payments/create-order. Backend validates stock, creates PENDING Order and Razorpay Order (e.g. order_rzp_xxx). Stock is NOT deducted yet.
▼ Razorpay Checkout Modal Launched on Frontend ▼
2️⃣ Step 2: Customer Authorization
Customer authorizes payment (Card, UPI, NetBanking). Razorpay returns razorpay_order_id, razorpay_payment_id, and razorpay_signature.
▼ Client Submits Verification Payload to Server ▼
3️⃣ Step 3: Cryptographic Verification & Idempotent Stock Deduction
Server verifies HMAC-SHA256 signature against RAZORPAY_KEY_SECRET. Upon match: Order status $\rightarrow$ CONFIRMED, payment status $\rightarrow$ PAID, and stock is deducted EXACTLY ONCE.

2. HMAC-SHA256 Cryptographic Signature Verification

Backend Verification Logic

public boolean verifySignature(
    String orderId, String paymentId, String signature) {
  try {
    String payload = orderId + "|" + paymentId;
    Mac sha256_HMAC = Mac.getInstance("HmacSHA256");
    SecretKeySpec secret_key = new SecretKeySpec(
        secret.getBytes(StandardCharsets.UTF_8), "HmacSHA256");
    sha256_HMAC.init(secret_key);
    byte[] hash = sha256_HMAC.doFinal(
        payload.getBytes(StandardCharsets.UTF_8));
    String expected = Hex.encodeHexString(hash);
    return MessageDigest.isEqual(
        expected.getBytes(), signature.getBytes());
  } catch (Exception e) {
    return false;
  }
}

Idempotent Stock Protection Guarantees

  • Zero Race Deductions: If a user abandons the Razorpay modal, stock remains untouched and orders stay in PENDING.
  • No Double-Deductions: Verification logic verifies if payment is already PAID. Duplicate webhook or retry calls are recognized and ignored.
  • Default Shipping Address Anchor: Veerapunayunipalli, Kadapa, Andhra Pradesh, 516321, India

2. 5-Stage Warehouse Order Fulfillment Pipeline

Fulfillment Pipeline Stages

  1. ALLOCATED: Stock unit assigned to closest regional hub; aisle/bay coordinates designated (e.g. Aisle 02, Bay B-04).
  2. PICKED: Depot staff performs wave pick; records physical picker verification timestamp.
  3. PACKED: Package weight verified, boxed (e.g. Electro-Shield Box E1), packing slip generated (e.g. PS-HYD-9011).
  4. READY_FOR_SHIPMENT: Carrier assignment (BlueDart Express, FedEx) with manifest barcode creation.
  5. SHIPPED / DISPATCHED: Live tracking number (TRK-BLD-778291) issued; automated email dispatch sent to customer.

Inbound Receiving & QC Inspection

When merchants restock or transfer goods between warehouses, shipments pass through an Inbound Quality Control (QC) audit. Passed items increment availableStock, while defective items are sequestered to damagedStock with detailed reason logs (e.g. carton water damage, cracked display).

Supported Movement Types: RESTOCK_INBOUND, ORDER_OUTBOUND, TRANSFER_BETWEEN_HUBS, RETURN_INBOUND, DAMAGED_WRITE_OFF.

SHOPSTACK Return Management, Customer Reviews & Notification System
SECTION 08

1. Reverse Logistics & Return Management Workflow

ShopStack supports a robust return lifecycle enabling customers to initiate return requests for delivered orders. The system coordinates warehouse intake, condition review, and automated inventory reconciliation.

1. Customer Initiation

Customer submits a return request for eligible delivered items with specific reason codes (e.g., size mismatch, transit damage, defective unit).

2. Inbound QC Audit

Returned items arrive at the nearest warehouse hub. Staff inspect seal integrity and product function, categorizing condition as Restockable or Damaged.

3. Restock & Refund

Upon approval, undamaged items re-enter availableStock. Payment status updates to REFUNDED, and customer is notified via email.

2. Verified Customer Rating & Review System

To maintain marketplace transparency and consumer trust, customers can post star ratings (1 to 5) and textual reviews. Product and vendor aggregate ratings are dynamically recalculated via atomic database aggregations.

2. Data Integrity & Concurrency Architecture

Transactional Isolation Guarantees

Spring Data @Transactional boundaries are enforced at the service layer. In the event of an unexpected database or external API failure during payment or order creation, the transaction rolls back cleanly, preventing orphan order or payment records.

Optimistic & Defensive Locking

Stock deductions utilize atomic update queries (UPDATE Product p SET p.stockQuantity = p.stockQuantity - :qty WHERE p.id = :id AND p.stockQuantity >= :qty), protecting against negative inventory states under high concurrent checkouts.
